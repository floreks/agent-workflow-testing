## Scanner & commands

Trivy was run via the official Docker image (so local Go tooling is not required).

### Commands (reproducible)

From repo root:

```bash
# (optional) use a local cache to avoid re-downloading the vuln DB every run
rm -rf .trivy-cache && mkdir -p .trivy-cache trivy-out

# JSON output (best for CI / automation)
docker run --rm \
  -v "$PWD":/repo \
  -v "$PWD/.trivy-cache":/root/.cache/ \
  aquasec/trivy:0.70.0 \
  fs --scanners vuln --pkg-types library \
  --severity CRITICAL,HIGH,MEDIUM \
  --format json --output /repo/trivy-out/trivy-go-libs.json \
  /repo

# Human-readable table output
docker run --rm \
  -v "$PWD":/repo \
  -v "$PWD/.trivy-cache":/root/.cache/ \
  aquasec/trivy:0.70.0 \
  fs --scanners vuln --pkg-types library \
  --severity CRITICAL,HIGH,MEDIUM \
  --format table --output /repo/trivy-out/trivy-go-libs.txt \
  /repo
```

## Recommended remediation

1. **Update vulnerable dependencies** in `backend/go.mod` to versions at or above Trivy’s reported fixed versions.
2. Run `go get`/`go mod tidy` (in a Go toolchain environment) and re-run Trivy to confirm the findings are resolved.
3. Consider adding a CI job that runs Trivy in Docker (using the JSON output) and fails on CRITICAL/HIGH.

## Notes / limitations

- This is a filesystem (`trivy fs`) scan which detects module manifests and reports known CVEs for referenced dependencies.
- Some vulnerabilities may be in transitive dependencies; upgrading the direct module version is often sufficient but not always.
- If the repository uses `replace` directives or vendor mode, ensure Trivy scans the same inputs your build uses.
